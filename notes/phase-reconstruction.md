# Реконструкция фазы (S2): алгоритм и отличия от оригинального Digit

Заметка про стадию S2 пайплайна DigitQt — восстановление плотной карты фазы
(`PhaseMap`, в единицах порядка полосы) из пронумерованных линий полос,
оцифрованных на стадии S1. Формат: `.mtr` (WinFringe), `.frn` (WinFringe).

## TL;DR

- Текущий алгоритм — **построчная кубическая сплайн-интерполяция**, порт
  `WavefrontFromContoursSolver_HorizontalSpline` из оригинального Digit.
  Именно этот метод (а не что-то более "красивое" вроде решения уравнения
  Лапласа) реально используется в оригинале для экспорта в `.mtr`.
- Раньше в DigitQt стояло глобальное 2D-решение уравнения Лапласа (CG). Оно
  математически элегантнее, но давало вавефронт, заметно отличающийся от
  того, что получает оригинальный Digit и что реально измерено — см.
  [«Почему не Лапласиан»](#почему-не-лапласиан-теория).
- У построчного метода есть врождённый недостаток: у полюса апертуры (где
  полосы сжаты и трассировка может не пересекать строку ≥2 раз) целые
  строки остаются без данных. В оригинальном Digit это так и есть. В
  DigitQt это дополнительно смягчено вертикальной докомпенсацией — см.
  [«Полюс апертуры»](#полюс-апертуры-вертикальная-докомпенсация).

## Построчная сплайн-реконструкция

Идея: полосы почти вертикальны (доминирующий горизонтальный наклон/несущая
частота), поэтому для каждой строки сетки Y можно независимо:

1. **Найти пересечения** всех пронумерованных линий с горизонталью
   `y = Y` (`findFringeCrossings` в `PhaseReconstructor.cpp:31`). Для
   наклонных сегментов — линейная интерполяция по Y с полуоткрытым правилом
   `[ymin, ymax)` (чтобы горизонталь, проходящая точно через общую вершину
   двух сегментов, не давала пересечение дважды). Для горизонтальных
   сегментов — точка пересечения берётся как середина сегмента.
2. Отсортировать пересечения по X.
3. Построить **натуральный кубический сплайн** через точки `(x, order)`
   (класс `NaturalCubicSpline`, метод Томаса для трёхдиагональной системы
   вторых производных — стандартный алгоритм для natural cubic spline).
   Меньше 2 пересечений — строка целиком остаётся `NaN` (нет достаточно
   данных для сплайна).
4. Посчитать сплайн в каждом видимом пикселе строки, **включая
   экстраполяцию** за крайние пересечения (последним сегментом сплайна) до
   края апертуры.

Строки друг с другом никак не связаны. Это специально: местная частота
(наклон `dz/dx`) внутри строки определяется напрямую реальными измеренными
X-координатами пересечений, а не выводится из требования глобальной
гладкости поверхности.

### Почему не Лапласиан (теория)

Раньше здесь стояло глобальное решение `∇²z = 0` (уравнение Лапласа) методом
сопряжённых градиентов: линии — граничные условия Дирихле, край апертуры —
естественное условие Неймана. Результат — самая гладкая (в смысле
энергии Дирихле `∫|∇z|²`) поверхность, точно проходящая через оцифрованные
линии.

Проблема в том, что "гладкость" в смысле `∇²z=0` (гармоничность) — это не
то же самое, что гладкость реального волнового фронта. Гармонична только
чистый наклон (`z = ax+by`). Реальные аберрации — нет:

- дефокус `z = ρ²` → `∇²z = 4` (константа, не ноль)
- сферическая, кома, астигматизм — тоже не гармоничны

Оцифрованные линии дают только *значения* `z` вдоль тонких кривых, никакой
информации о градиенте между ними. Заставляя решатель заполнять промежутки
гармонической поверхностью, мы навязываем физически неверную гипотезу:
что кривизна волнового фронта равна нулю везде, кроме как непосредственно
на линиях. Реальную кривизну (дефокус/сферическая и т.п.) решателю девать
некуда — она вытесняется туда, где у него ещё остаётся свобода: к краю
апертуры и в узкие зоны вокруг самих линий. Отсюда были загибы изолиний
именно на концах линий и у края апертуры, а не в середине — и именно там
у реальных аберраций (~`ρ²`, `ρ⁴`) кривизна максимальна, так что
несовпадение гармонической гипотезы с реальностью там тоже максимально.

Построчный сплайн этой проблемы не имеет: он не делает *никаких*
предположений про Лапласиан. Производная `dz/dx` в каждой точке по
построению равна реально измеренному расстоянию между полосами в этой
строке — метод "смотрит" именно в направлении быстрого изменения фазы
(поперёк полос) и использует реальные данные как якорь для производной, а
не только для значения.

Практическая проверка: реконструкция + повторная генерация
интерферограммы по глобальному Лапласиану заметно расходилась с исходной
интерферограммой; после перехода на построчный сплайн (тот же алгоритм,
что и в оригинальном Digit) расхождение исчезло — см. картинки
`digit_test.png` / `my_test.png` в истории разработки (генерировались из
`test_images/digit_my_compare/`, в репозитории сейчас не хранятся).

### Полюс апертуры: вертикальная докомпенсация

Врождённый недостаток построчного метода: если у полюса апертуры (где она
узкая) трассированные линии не дают ≥2 пересечений в какой-то строке, вся
строка остаётся `NaN` целиком — даже если геометрически часть её пикселей
видима. Граница "есть данные / нет данных" получается **плоской
горизонталью** вместо повторения формы апертуры. WinFringe, трассируя
изолинии, обводит этот искусственный обрыв отдельной изолинией, окрашенной
по градиенту Z вдоль него — визуально выглядит как лишняя горизонтальная
линия сверху/снизу карты.

**Оригинальный Digit имеет ровно то же ограничение**
(`if (crossings.size() < 2) continue;` в
`WavefrontFromContoursSolver_HorizontalSpline::solve`) — это не расхождение
с портом, это врождённое свойство самого алгоритма.

DigitQt смягчает это вторым проходом (`PhaseReconstructor.cpp:181-231`,
после основного построчного цикла): для видимых пикселей, чья строка не
была решена, значение подтягивается **по вертикали** от ближайшей решённой
строки в том же столбце — линейно между соседями сверху и снизу, если
решённые строки есть с обеих сторон, иначе просто держится ближайшее
значение с той стороны, где данные есть. Это не восстанавливает
"настоящие" данные там, где трассировка физически не дошла до края (для
этого нужны более длинные/точные трассированные линии на стадии S1), но
убирает сам механизм, порождающий видимую горизонтальную линию: край
перестаёт быть плоским обрывом.

Проверено синтетическим smoke-тестом (круглая апертура, полосы, не
доходящие до полюса ~30% радиуса с каждой стороны): до фикса — сотни
неразрешённых видимых пикселей в зонах у полюсов; после — 0.

## Отличия модели данных DigitQt vs Digit

| | Digit (оригинал) | DigitQt |
|---|---|---|
| Линия полосы | плоский список точек `(X, Y, F.Number, F.Index)`, один и тот же номер `F.Number` может встречаться в нескольких разрывных кусках, различаемых по `F.Index` | `NumberedFringeLine { points, order }` — одна структура уже является одной непрерывной ломаной с одним номером; разрыв полосы = отдельный `NumberedFringeLine` с тем же `order` |
| Экстракция пересечений строки | итерация по плоскому списку с отслеживанием смены `Number`/`Index` | прямая итерация по `lines`, каждая уже сама по себе цельная ломаная — код проще, семантически то же самое |
| Формат `.frn` | два варианта на выбор пользователя: "родной" Digit (сырые пиксельные координаты) и WinFringe (Y перевёрнут + нормализация) | реализован только WinFringe-вариант (см. `FrnExporter.cpp`) — родной формат не портирован, т.к. не нужен |
| Апертура | `XYEllipse`/`XYRect`/`XYPolygon`, 2 типа обскурации (`INTERNAL`/`EXTERNAL`) | `aperture::Shape` (`Ellipse`/`Rectangle`/`Polygon`), 3 типа (`EXTERNAL`/`INTERNAL`/`APERTURE` — новый тип "локальное открытие", аналога в `.frn` нет, такие фигуры при экспорте пропускаются) |

## Известные ограничения / что можно улучшить

- Полюс апертуры: вертикальная докомпенсация лечит **визуальный
  артефакт**, но не восполняет реально отсутствующие данные. Если
  трассировка S1 систематически не доходит до края апертуры, лучшее
  решение — улучшить сам трекер (`ScanlineExtremumTracker` и т.п.) для
  сильно сжатых полос у края, а не заплатку на S2.
- Построчный метод в принципе не учитывает согласованность между
  соседними строками (кроме полюсной докомпенсации) — в отличие от
  честного 2D-решения. Для интерферограмм, где полосы **не** близки к
  вертикальным (например почти горизонтальные полосы или сильно
  искривлённые), метод менее надёжен: строка может содержать мало
  пересечений или пересечения не будут монотонны по X в физическом смысле.
  Оригинал имеет то же ограничение — портирование этим не хуже оригинала,
  но и не лучше.
- `.frn`: реализован только WinFringe-flavour. Родной формат Digit
  (`Filter_FRN`, без переворота/нормализации Y) не портирован.
- Экспорт в CodeV `.int` — не начат, спецификация формата не собрана
  (в референсном проекте такого формата нет вовсе).
