## 0. Физика интерференции: с нуля

### 0.1 Что вообще такое интерферограмма

Свет — электромагнитная волна. Если разделить один пучок света на два (полу-
прозрачным зеркалом), пропустить их по разным путям и снова свести вместе на
экране/матрице, результат зависит от **разности хода** между ними — на сколько
длин волн один путь длиннее другого.

Пусть `A` = амплитуда, `λ` = длина волны, `OPD` (Optical Path Difference) =
разность хода двух пучков в точке `(x,y)` экрана. Интенсивность, которую видит
камера:

```
I(x,y) = I0 · [1 + V · cos(φ(x,y))],   φ(x,y) = 2π · OPD(x,y) / λ
```

где `V` (visibility/contrast, 0..1) — контраст полос (зависит от того, насколько
похожи амплитуды двух пучков и насколько когерентен источник).

- Когда `φ = 2πN` (N — целое) → `cos = 1` → **максимум** яркости — светлая полоса.
- Когда `φ = 2π(N+0.5)` → `cos = -1` → **минимум** яркости — тёмная полоса.

Т.е. **полосы — это линии равной разности хода** (изолинии `OPD`). Соседние
светлые полосы отличаются ровно на `OPD = λ`. Число `N` в этой формуле и есть
**порядок полосы** (fringe order) — центральное понятие всего проекта
(`NumberedFringeLine::order`, [`src/core/NumberedFringeLine.h`](../src/core/NumberedFringeLine.h)).

### 0.2 Как разность хода связана с формой поверхности

Два типовых сценария испытаний, оба заложены в `Measurement::isDoublePass()`
([`src/core/Measurement.h:77`](../src/core/Measurement.h)):

**Отражательная схема (double-pass, тест на отражение, напр. интерферометр
Физо/Тваймана-Грина, проверяющий зеркало или полированную поверхность).**
Свет идёт ДО поверхности и ОБРАТНО. Если участок поверхности выступает над
идеальной формой на высоту `h`, луч проходит на `2h` длиннее (туда и обратно).
Значит:

```
OPD = 2h  =>  h = OPD / 2 = N·λ / 2
```

Это ровно формула из `WavefrontReconstructionStage`
([`src/core/pipeline/stages/WavefrontReconstructionStage.cpp:20`](../src/core/pipeline/stages/WavefrontReconstructionStage.cpp)):
`heightPerOrder = wavelengthNm / 2`. Каждая целая полоса = полшага длины волны
рельефа поверхности. Это самый частый случай в оптическом контроле (проверка
зеркал, линз "на отражение").

**Проходная схема (single-pass, тест на просвет, напр. проверка плоскопараллельной
пластины или объектива на просвет).** Свет проходит через объект один раз;
измеренная величина — сразу аберрация волнового фронта:

```
OPD = W  =>  W = N·λ
```

т.е. без деления на 2.

> **Исправлено.** Раньше `WavefrontReconstructionStage.cpp` **всегда** делил
> на 2, не читая `isDoublePass()` вообще — по умолчанию флаг `= true`, так
> что для самого частого случая (отражение) результат был верным, но
> одинарный проход посчитать было нельзя без ручного трюка (вписать
> удвоенную длину волны). Обнаружено эмпирически: коэффициенты S5,
> посчитанные DigitQt по `test_data/Terminal.bmp`, оказались РОВНО в 2 раза
> меньше эталонного `test_data/report.txt` (оригинальный отчёт Digit/DAPPSIM
> для того же `Terminal.pol`) — совпадение по наклону и астигматизму (самым
> устойчивым к шуму термам) с точностью 0.5% после умножения на 2. Теперь
> `heightPerOrder` реально ветвится по `isDoublePass()`; переключатель
> добавлен на странице S4 в `ParametersDock` ("Double pass (reflection)").

### 0.3 Зачем нужен наклон опорного пучка (carrier / несущая частота)

Если испытуемая поверхность идеальна (или отличия — доли длины волны), то
`OPD(x,y)` почти постоянна по всей апертуре — вся картинка окажется одним
сплошным пятном, без полос вообще (или одной-двумя широкими полосами
"колец", как в классических интерферограммах Ньютона). Оцифровать форму
поверхности по одной полосе невозможно — нет пространственного разрешения.

Решение: намеренно **наклонить** одно из зеркал интерферометра на маленький
угол. Это добавляет линейный член к разности хода:

```
OPD_total(x,y) = OPD_aberration(x,y) + (a·x + b·y)
```

Линейный член `a·x + b·y` называют **несущей (carrier)** — он создаёт
регулярную решётку прямых, почти параллельных полос по всей апертуре
(похоже на интерференционную решётку). Реальная форма поверхности видна как
**искривление** этих прямых полос относительно идеально прямых линий:
выпуклость/вогнутость (дефокус) сжимает/раздвигает полосы к краю, кома
изгибает их несимметрично, астигматизм делает шаг разным по двум осям и т.д.

Все 4 алгоритма трассировки (§3) и оба "глобальных" метода реконструкции
фазы — Фурье (§5.2) и вейвлет (§5.3) — **рассчитаны именно на такую картину**
несущей плюс возмущение. Без наклона (истинно круговые кольца Ньютона без
несущей) тоже можно работать — трекеры умеют замыкать контур в кольцо
(`loop closure`, см. §3.2–3.4), но метод Фурье (§5.2) в таком случае не
находит бокового пика несущей и завершается ошибкой ("Could not find a clear
carrier frequency").

### 0.4 Апертура, зрачок, обструкции

**Апертура** — рабочая область измерения (обычно круг — изображение зрачка
оптической системы). Всё вне апертуры — не данные, физически бессмысленно
(это может быть чёрная рамка вокруг снимка, оправа зеркала и т.п.).

**Обструкция (внутреннее препятствие, INTERNAL)** — область ВНУТРИ основной
апертуры, которая физически не несёт данных: например центральное
экранирование в зеркальном телескопе (вторичное зеркало), крепёж, паучок.

**Локальное окно (APERTURE, "opening")** — специфичное для DigitQt понятие:
маленькая область, которая **переоткрывает** видимость внутри обструкции или
за пределами основной EXTERNAL-апертуры (аналога в старом формате `.frn` нет —
см. §8.2). Пример: маленькое отверстие в экране, через которое всё же видна
интерферограмма.

Всё это реализовано в `aperture::VisibilityChecker`
([`src/aperture/include/visibility/VisibilityChecker.h`](../src/aperture/include/visibility/VisibilityChecker.h),
[`.cpp`](../src/aperture/visibility/VisibilityChecker.cpp)) как простой
предикат `isVisible(x,y)`, вычисляемый в 3 шага:

1. **INTERNAL** — если точка внутри ЛЮБОЙ INTERNAL-фигуры → сразу `false`
   (обструкция абсолютна, ничего её не может "переоткрыть").
2. **EXTERNAL** — точка должна быть внутри **всех** EXTERNAL-фигур
   (пересечение/intersection). Если фигур EXTERNAL нет вообще — по умолчанию
   `visible = false` (без явно заданной апертуры ничего не видно).
3. **APERTURE** — если после шага 2 точка невидима, но попадает в **любую**
   APERTURE-фигуру (объединение/union) — видимость принудительно включается
   обратно (`true`), кроме случая, когда её уже заблокировал шаг 1.

Каждая форма (`Ellipse`, `Rectangle`, `Polygon` —
[`src/aperture/geometry/`](../src/aperture/geometry/)) реализует
`isInside(Point)` и умеет поддерживать поворот. Эта же троичная логика
используется на КАЖДОЙ стадии конвейера, где нужно знать "это точка данных
или нет" — трассировка (§3), обе безызбегательные (seed-free) реконструкции
фазы (§5.2, §5.3), модальный анализ (§7).

## 1. Архитектура конвейера DigitQt

Файлы: [`src/core/pipeline/Pipeline.h`](../src/core/pipeline/Pipeline.h),
[`PipelineStage.h`](../src/core/pipeline/PipelineStage.h),
[`PipelineStageId.h`](../src/core/pipeline/PipelineStageId.h).

Обработка — строго последовательный конвейер стадий:

```
Setup (S0+S0a+S0b+S0c+S1) → S2 (Phase Reconstruction) → S4 (Wavefront Reconstruction)
   → S4b (калибровка, не реализована) → S5 (Modal Analysis)
   → S6 (Diffraction Analysis, не реализована) → S7 (Interferogram Synthesis, не реализована)
```

`Setup` объединяет 5 логических подстадий спецификации (S0 сырое изображение,
S0a маска апертуры, S0b реперные метки — пока не реализованы, S0c
геометрическая калибровка — пока не реализована, S1 трассировка полос) в один
узел дерева, потому что на практике это одна непрерывная работа пользователя.

**Ключевое архитектурное правило: "нет неявного пересчёта".** Каждая стадия
хранит статус (`NotComputed` / `Stale` / `Computed` / `Error`). Изменение
входных данных ВЫШЕ по конвейеру (например, правка границы апертуры) помечает
эту и все стадии НИЖЕ как `Stale` (`Pipeline::invalidateFrom`), но **ничего не
пересчитывается автоматически** — пользователь явно жмёт "Compute" на каждой
стадии. Это сознательный выбор (не "лень", а модель предсказуемости для
метролога — результат всегда получен явным, воспроизводимым действием, а не
фоновой магией).

Примечательно, что классической стадии **S3 (Phase Unwrapping)** в этом
конвейере как отдельного шага НЕТ: она "встроена" в то, как работает
`FringeConstructor` (§4) — соседние полосы уже пронумерованы целыми
последовательными числами по построению, так что развёрнутая
(unwrapped) фаза получается сразу, без отдельного шага разворачивания
свёрнутой (`mod 2π`) карты. (Единственное исключение — методы Фурье и
вейвлета в S2, у которых разворачивание фазы — явный внутренний шаг
алгоритма, см. §5.2–5.3, но он не выделен в отдельную стадию конвейера.)

## 2. Загрузка изображения и апертура (S0/S0a)

### 2.1 Паддинг фона изображения

Файл: [`src/core/ImagePadding.cpp`](../src/core/ImagePadding.cpp) /
[`.h`](../src/core/ImagePadding.h).

**Проблема.** Если апертура (или сама интерферограмма) касается КРАЯ сырого
изображения, у алгоритмов трассировки (особенно `BinaryThinningTracker` с его
distance transform и `ScanlineExtremumTracker` со сканированием строк по всей
ширине кадра) нет "видимости" за пределы кадра, чтобы отличить настоящий край
апертуры от случайно обрезанного кадром. Результат — фрагментация полос и
краевые артефакты у самого края снимка.

**Решение.** `padImageBackground()` добавляет рамку фонового цвета вокруг
изображения:

1. Переводит изображение в 8-битные градации серого.
2. Определяет цвет фона как **моду** (наиболее частое значение) пикселей,
   выбранных строго по периметру исходного кадра (`dominantBorderGray`) — так
   рамка подстраивается под то, на каком фоне реально снята интерферограмма
   (не обязательно чёрный).
3. Создаёт увеличенное изображение (`marginFraction`, по умолчанию 0.15, т.е.
   15% от большей стороны с каждого края) и копирует исходное в центр,
   заполняя рамку цветом фона.

Теперь апертура гарантированно НЕ совпадает с краем кадра, и всем последующим
алгоритмам есть куда "видеть" за её пределы.

### 2.2 Маска видимости (апертура)

См. §0.4 — вся логика реализована в `aperture::VisibilityChecker`. Пользователь
рисует фигуры (эллипс/прямоугольник/полигон) поверх изображения на канвасе
(`BoundaryEditController`/`BoundaryItem`, [`src/gui/canvas/`](../src/gui/canvas/)),
каждая помечается как EXTERNAL/INTERNAL/APERTURE — это и есть `S0a`
("Aperture & Visibility Masking"). Дальше на каждом шаге конвейера этот же
`ShapeCollection` оборачивается в `VisibilityChecker` и передаётся как
предикат `isVisible(x,y)`.

## 3. Трассировка полос (S1) — 4 алгоритма

Общий контракт: [`src/core/pipeline/stages/fringe_tracing/IFringeTracer.h`](../src/core/pipeline/stages/fringe_tracing/IFringeTracer.h).

```cpp
struct TracedPoint { double x, y; float width; float intensity; };
using TracedLine = std::vector<TracedPoint>;
struct SeedPoint  { int x, y; };  // затравка — нужна не всем алгоритмам

class IFringeTracer {
  bool initialize(const QImage&, isVisible predicate);
  std::vector<TracedLine> extract(const std::vector<SeedPoint>& seeds);
};
```

Задача трассировки — найти **центральную линию (гребень)** каждой полосы:
подпиксельно точную кривую, идущую вдоль максимума (или минимума) яркости.
Четыре реализации решают эту задачу принципиально разными способами; все
доступны в UI как выбор алгоритма и могут сравниваться на одном изображении.

| Алгоритм | Класс | Нужна затравка? | Подпиксельная точность? |
|---|---|---|---|
| Sequential Fringe Tracking (FTM) | `SequentialFringeTracker` | да, 1 на полосу | нет (целые пиксели) |
| Ridge Tracking (Structure Tensor) | `StructureTensorTracker` | да, 1 на полосу | да (билинейная + квадратичная доводка) |
| Scanline Extremum Method (FTM) | `ScanlineExtremumTracker` | нет (глобальный) | да (квадратичный фит пика) |
| Binary Thinning Method (FBM) | `BinaryThinningTracker` | нет (глобальный) | нет (пиксели скелета) |

### 3.1 Sequential Fringe Tracking (FTM) — пошаговый локальный трекер

Файлы: [`SequentialFringeTracker.h`](../src/core/pipeline/stages/fringe_tracing/SequentialFringeTracker.h) /
[`.cpp`](../src/core/pipeline/stages/fringe_tracing/SequentialFringeTracker.cpp).
Порт классического модуля `SCAN360/STEP.C` из оригинального Digit.

**Идея:** от одной затравочной точки на гребне полосы алгоритм "идёт" вдоль
неё шаг за шагом, как человек, идущий по гребню холма с закрытыми глазами,
ощупывая склон под ногами.

**Локальная система координат.** В каждой точке определены:
- **"Поперечная" ось** (across the fringe) — направление, вдоль которого
  яркость быстрее всего падает от гребня. Квантована с шагом 45°: одно из 4
  направлений `{0°(верт.), 45°, 90°(гориз.), 135°}` (`TraceDirection`).
- **Направление движения** (along the fringe) — перпендикулярно поперечной
  оси (поворот на 90°).
- **Ширина полосы** `m_curWidth` — сколько пикселей яркость держится выше
  фонового порога поперёк гребня.

**`measureWidth(x,y)`** — измерение ширины и поперечной оси, в 2 фазы:
1. *Поиск порога фона* — по каждой из 4 осей идём наружу от точки, пока
   среднее яркости (окно из растущего числа отсчётов) убывает; как только
   несколько шагов подряд яркость перестаёт падать — это и есть "пол" (фон)
   для этой оси. (Особенность реализации: итоговый общий порог `m_average`
   берётся с ПОСЛЕДНЕЙ из 4 осей, а не как среднее/минимум по всем — так
   ведёт себя оригинальный алгоритм, сохранено сознательно.)
2. *Измерение пробега* — по каждой из 4 осей считаем, сколько пикселей в обе
   стороны яркость держится выше найденного порога; ось с **минимальным**
   суммарным пробегом — это и есть искомая поперечная ось (полоса "тоньше
   всего" именно поперёк себя, по определению).

**`firstStep()`** — начальная привязка затравки к реальному гребню:
`measureWidth` определяет ось → `findMaxAlong()` вдоль этой оси ищет
локальный максимум яркости (в радиусе половины ширины — не больше, чтобы не
перепрыгнуть на соседнюю полосу) → `measureWidth()` повторно уточняет ось в
новой точке → поворот на 90° даёт направление вдоль полосы → шаг на ширину
полосы в этом направлении → `centerPerpendicular()` подправляет вторую точку
поперёк движения.

**`step()`** — тело цикла трассировки:
1. Измеряется ширина/направление в текущей точке; если яркость упала ниже
   экспоненциально сглаженного порога фона `m_averageEma` — полоса "потеряна"
   (код `-5`; EMA, а не сравнение с одним предыдущим отсчётом — иначе виньетка
   у края апертуры ложно воспринималась бы как конец полосы).
2. Ширина шага ограничена относительно предыдущей (`maxWidthChange`, не
   больше чем в 1.5 раза за шаг) — защита от единичного шумного пикселя.
3. Направление движения сглаживается по последним `directionSmoothingWindow`
   шагам (усреднение векторов смещения) — устойчивость к локальному шуму
   контура.
4. Прогнозируется следующая точка вдоль сглаженного направления, на
   расстояние, зависящее от текущей ширины (уже, если полоса узкая; медленнее
   при полосе широкой — коэффициенты 1.0/0.8/0.6/0.4 в зависимости от
   диапазона ширины).
5. Если прогноз вышел за апертуру — по отрезку ищется последняя валидная
   точка на границе (`linStepToBoundary`, классический DDA), трассировка
   останавливается (`-1`).
6. Иначе `centerPerpendicular()` подправляет прогноз поперёк движения на
   реальный максимум яркости. Если "прыжок" центрирования оказался больше
   `maxCenteringJumpFactor × ширина` — это подозрительно похоже на перескок
   на соседнюю полосу, трассировка останавливается (`-2`).
7. Проверка замыкания контура: если новая точка ближе ширины полосы к самой
   первой точке линии (длина уже > 5) — контур замкнулся сам на себя (кольцо
   Ньютона без несущей, см. §0.3) — остановка (`-10`), обратный проход не
   нужен.

**Двунаправленность.** По умолчанию после прохода "вперёд" от затравки
выполняется отдельный проход "назад" (с той же логикой, но противоположным
начальным направлением), и два куска сшиваются в одну линию — так одна
затравка где-то в середине полосы даёт полную линию от края до края апертуры.

**Архитектурное ограничение (не точечно исправимое):** трекер принципиально
работает в целых пиксельных координатах — ни один из внутренних шагов не
делает суб-пиксельного уточнения. Если нужна точность локализации гребня
лучше 1 пикселя (важно для итоговой карты фазы) — используйте
`StructureTensorTracker` (§3.2).

### 3.2 Ridge Tracking (Structure Tensor) — трекер со структурным тензором

Файлы: [`StructureTensorTracker.h`](../src/core/pipeline/stages/fringe_tracing/StructureTensorTracker.h) /
[`.cpp`](../src/core/pipeline/stages/fringe_tracing/StructureTensorTracker.cpp).

Концептуальный аналог §3.1, но с непрерывным (не квантованным на 45°)
направлением и настоящим суб-пиксельным центрированием в 2D-окрестности
(а не по одной линии).

**Структурный тензор.** В окне радиуса `orientationWindowRadius` вокруг точки
считаются центрально-разностные градиенты `gx, gy` в каждом пикселе окна и
собирается матрица (структурный тензор):

```
S = [ Σgx²   Σgx·gy ]
    [ Σgx·gy  Σgy²   ]
```

Локальное направление вдоль гребня — это **собственный вектор МЕНЬШЕГО
собственного значения** `S`. Физический смысл: градиент яркости
концентрируется ПОПЕРЁК полосы (там яркость меняется быстро), а ВДОЛЬ полосы
почти не меняется — значит, направление наименьшей "энергии градиента" и есть
направление вдоль гребня. Собственные значения/векторы 2×2 симметричной
матрицы находятся аналитически (без итеративного решения):

```
trace = Sxx+Syy,  det = Sxx·Syy - Sxy²
λmin  = trace/2 - √(trace²/4 - det)
```

**Оценка ширины (`estimateWidth`)** — по методу "полу-высоты" (full-width-
half-maximum, FWHM-подобная метрика): вдоль перпендикуляра к направлению
движения сканируется яркость в обе стороны до расстояния 25 px, берётся
МИНИМУМ встреченной яркости как оценка фона (не значение в одной
фиксированной точке — при частых полосах фиксированная точка может случайно
попасть на соседний гребень вместо впадины), затем находится расстояние, на
котором яркость падает ниже полусуммы (центр+фон)/2 в обе стороны — сумма
даёт ширину.

**`findLocalMaximum()`** — грубый поиск максимума яркости перебором в окне,
затем суб-пиксельная доводка **независимыми одномерными квадратичными фитами**
по x и по y отдельно (парабола через 3 точки вокруг найденного максимума) —
классический метод субпиксельной локализации пика.

**Шаг трассировки (`traceDirectionally`)** — предсказание следующей точки на
расстоянии `stepFraction × ширина` вдоль текущего направления, 2D-поиск
локального максимума в окрестности прогноза (радиус `searchRadiusFraction ×
ширина`), проверка "прыжка" (не дальше `maxCenteringJumpFactor × ширина` от
прогноза — иначе это соседняя полоса), проверка потери контраста
(`contrast = пик - фон`, сравнивается с экспоненциально сглаженным средним —
устойчиво к постепенному затуханию яркости к краю апертуры, в отличие от
сравнения с сырой яркостью), переоценка направления в новой точке со
сглаживанием по истории (устойчивость к шуму одного отсчёта), проверка
замыкания контура — как и в §3.1.

### 3.3 Scanline Extremum Method (FTM) — глобальный построчный метод

Файлы: [`ScanlineExtremumTracker.{h,cpp}`](../src/core/pipeline/stages/fringe_tracing/ScanlineExtremumTracker.cpp),
[`scanline_extremum/RedCenterDetector.cpp`](../src/core/pipeline/stages/fringe_tracing/scanline_extremum/RedCenterDetector.cpp),
[`MiddleAlgorithm.cpp`](../src/core/pipeline/stages/fringe_tracing/scanline_extremum/MiddleAlgorithm.cpp),
[`FringeConstructor.cpp`](../src/core/pipeline/stages/fringe_tracing/scanline_extremum/FringeConstructor.cpp).
Порт `RedCenterDetector`/`FringeConstructor` оригинального Digit.

В отличие от §3.1–3.2, этому методу **не нужны затравки** — он сканирует ВСЁ
изображение построчно и сам находит и нумерует все полосы. Два независимых
этапа: (а) найти экстремумы в каждой строке отдельно, (б) связать их между
строками в непрерывные линии со сквозной нумерацией.

#### 3.3.1 Обнаружение экстремумов в строке (`RedCenterDetector`)

Для каждой строки `y`:

1. **`removeBackground(line, left, right)`** ([`MiddleAlgorithm.cpp:24`](../src/core/pipeline/stages/fringe_tracing/scanline_extremum/MiddleAlgorithm.cpp)) —
   оценка и вычитание фона перед поиском пиков. Для длинных сегментов (> 70 px)
   строка делится на 5 равных частей, в каждой части считается средняя
   яркость НЕНУЛЕВЫХ пикселей, между серединами соседних частей строится
   отрезок прямой (кусочно-линейная аппроксимация фона), и все пиксели ниже
   этой линии обнуляются. Для коротких сегментов — одна константа (средняя
   яркость всего сегмента). Смысл: убрать медленный тренд освещённости
   (виньетирование, неравномерная подсветка), оставив только локальные
   всплески — сами гребни полос.
2. Режим `FringeCenterMode` определяет, что ищем:
   - `Max` — только светлые гребни (яркие максимумы исходного изображения).
   - `Min` — только тёмные впадины (ищем максимумы в ИНВЕРТИРОВАННОМ
     изображении `255-I` — так один и тот же алгоритм поиска пиков работает
     для обоих случаев).
   - `MinMax` — оба сразу (см. физическое обоснование в §0.1: тёмные полосы
     сидят ровно посередине между двумя соседними светлыми, `MinMax` удваивает
     плотность цифровых отсчётов фазы без дополнительных полос на снимке).
3. **`detectPeaks(line)`** ([`MiddleAlgorithm.cpp:183`](../src/core/pipeline/stages/fringe_tracing/scanline_extremum/MiddleAlgorithm.cpp)) —
   сканирует строку слева направо, находит непрерывные "пробеги" ненулевых
   (после вычитания фона) и видимых (внутри апертуры) пикселей. Для каждого
   пробега длиной ≥ 5 отсчётов строится **квадратичная регрессия**
   `y = c0 + c1·x + c2·x²` методом наименьших квадратов по ВСЕМ точкам
   пробега (`fitQuadraticPeak`, решение системы 3×3 методом Гаусса с выбором
   ведущего элемента), и субпиксельный пик — вершина параболы
   `x_peak = -c1/(2·c2) + 0.5` (сдвиг +0.5 — историческое соглашение о
   привязке к центру пикселя). Для коротких пробегов (< 5 отсчётов) —
   упрощённо, середина плато максимума.

Результат — список `ExtremumPoint` на строку (тип: `Red` = светлый максимум,
`Black` = тёмный минимум), плюс средний шаг между соседними экстремумами
(`averageStep`) — оценка локальной "плотности" полос в этой строке.

#### 3.3.2 Связывание в линии и сквозная нумерация (`FringeConstructor`)

Это самая содержательная часть алгоритма — она одновременно решает задачу
"кто с кем соединяется в одну полосу" (трассировка) И "какой у неё номер"
(нумерация/развёртывание фазы, см. §1 — здесь S3 не нужен отдельно именно
благодаря этому механизму).

1. **Медианный шаг.** Из всех строк с ≥ 2 точками собирается `averageStep`,
   берётся МЕДИАНА (не среднее — устойчивее к выбросам) как ожидаемый шаг
   между полосами `medianStep`.

2. **Выбор "главной" строки** (`selectMainScanline`) — строка с максимальным
   числом экстремумов, чей `averageStep` укладывается в допуск
   `medianStep · (1 ± toleranceFactor)`. Ищется независимо с начала и с конца
   изображения; если оба поиска дают одинаковое максимальное число экстремумов
   и в апертуре НЕТ внутренней обструкции — берётся строка ровно посередине
   между двумя кандидатами (симметрия задачи); если обструкция есть — берётся
   кандидат от начала (апертура с "дыркой" уже не симметрична).

3. **Инициализация главной строки** — её экстремумы получают
   последовательные номера `0, fringeStep, 2·fringeStep, ...` слева направо,
   и КАЖДЫЙ становится началом собственной "цепочки" (`chainId`) — уникального
   идентификатора физически связной последовательности точек.

4. **Распространение вверх и вниз** (`propagate`) — от главной строки:
   сначала вверх (к строке 0), затем вниз (к последней строке), КАЖДАЯ точка
   очередной строки пытается найти соответствие в уже пронумерованных строках:
   - тот же тип экстремума (Red/Black);
   - расстояние по X не больше допуска `tolerance = medianStep · toleranceFactor`;
   - совпадение (`match`) не должно физически ПЕРЕСЕКАТЬ ни один уже
     построенный отрезок другой цепочки (`wouldCross`, проверка пересечения
     отрезков) — не даёт двум разным полосам "перепутаться местами", если
     они сблизились или пересеклись на изображении;
   - (только в режиме `MinMax`) не должно нарушать чередование Red/Black —
     нельзя присвоить точке номер, который уже занят соседом ТОГО ЖЕ типа на
     соседней позиции (`wouldViolateAlternation`) — не даёт двум светлым
     полосам "слиться" в одну через темноту.
   - Если совпадение не найдено НИ В ОДНОЙ из более ранних (уже
     пронумерованных) строк — точка либо получает **новый** номер (если она
     генетически "за краем" уже виденного диапазона X, `leftX`/`rightX`,
     т.е. это реальная новая полоса, появившаяся у края апертуры), либо
     отбрасывается как **"орфан"** (внутренняя точка, которую не удалось ни с
     чем связать — типично при разрыве полосы обструкцией или шумом).

5. **Группировка в полилинии по `chainId`** (не по номеру!) — это специально
   исправленная в порте ошибка оригинала: там группировка шла по одному
   только "номеру" (fringe number), а два физически НЕСВЯЗАННЫХ куска полосы
   (например, одна и та же полоса "до" и "после" обструкции) могли случайно
   получить одинаковый номер и склеиться в одну неправильную ломаную. Явный
   `chainId`, наследуемый ТОЛЬКО через реально принятое совпадение,
   структурно исключает такую ошибку.

Итог — список `NumberedFringe { points, number }`: уже готовые, уже
пронумерованные (= уже "развёрнутые по фазе") полилинии. Именно эти номера
`ScanlineExtremumTracker::lastFringeNumbers()` используются напрямую в
`SetupStage.cpp` вместо общей эвристики "средний X" (§4) — они физически
осмысленнее (учитывают реальную топологию полос, а не только их среднее
положение).

### 3.4 Binary Thinning Method (FBM) — бинаризация + утончение скелета

Файлы: [`BinaryThinningTracker.{h,cpp}`](../src/core/pipeline/stages/fringe_tracing/BinaryThinningTracker.cpp).
Порт `CFringeSkeletonizer` из отдельного проекта InterferometryApp.

Принципиально другой подход — не построчный анализ интенсивности, а
классическая обработка бинарных изображений (морфология):

1. **Сглаживание** — гауссово размытие (подавление шума матрицы).
2. **Адаптивная бинаризация** (`cv::adaptiveThreshold`, `ADAPTIVE_THRESH_MEAN_C`) —
   порог вычисляется ЛОКАЛЬНО в окне `adaptiveBlockSize` вокруг каждого
   пикселя (среднее по окну минус константа `adaptiveC`), а не одним общим
   порогом на всё изображение — так метод устойчив к неравномерной
   освещённости по полю (виньетированию).
3. **Маска апертуры** применяется дважды (после бинаризации и после морфологии,
   т.к. морфологические операции могут "натечь" через край маски).
4. **Морфологическое открытие+закрытие** (`MORPH_OPEN` затем `MORPH_CLOSE`,
   эллиптическое ядро) — открытие убирает мелкий шум-крапинки, закрытие
   заращивает мелкие разрывы внутри полос.
5. **Утончение по алгоритму Zhang–Suen** (`skeletonize`) — классический
   алгоритм скелетизации бинарных изображений. Итеративно, в 2 под-итерации
   за проход, помечает и удаляет "граничные" пиксели переднего плана, у
   которых:
   - число живых соседей `B` (из 8-связной окрестности) в диапазоне `[2,6]`;
   - число переходов "0→1" по кругу соседей (`A`, "crossing number") равно
     ровно `1` (пиксель не разветвляет линию в этом направлении);
   - плюс два взаимодополняющих условия на конкретные соседи (разные для
     под-итераций 0 и 1 — поочерёдно "съедают" пиксели с разных сторон линии),
   
   пока изменения не прекратятся. Результат — линии толщиной ровно в один
   пиксель точно по центру исходной полосы.
6. **Обрезка "шпор"** (`pruneSkeleton`) — короткие тупиковые ответвления
   скелета (артефакты утончения на неровных краях бинарной маски) короче
   `pruneLength` удаляются.
7. **Извлечение полилиний** (`extractPolylines`) — сначала от каждой
   некопосещённой точки скелета с РОВНО ОДНИМ соседом (конец линии) идёт
   обход по 8-связности до следующего тупика или развилки, выбирая на
   развилке направление, наиболее коллинеарное предыдущему шагу (чтобы не
   "срезать угол" через перекрёсток на чужую ветку); затем отдельным проходом
   обрабатываются оставшиеся непосещённые пиксели — это замкнутые контуры без
   единого конца (кольца Ньютона, §0.3).
8. **Сшивка разрывов** (`linkBrokenLines`) — если полоса физически прервалась
   (обструкция, шум, слишком тонкий мостик, не переживший утончение), два
   конца ищутся с гарантиями: направления концов должны быть примерно
   коллинеарны (`cos угла > 0.5`, т.е. < 60°) — иначе это просто две разные
   близкие полосы, а не одна прерванная; "мостик" между ними должен ≥ 60%
   пролегать по самой бинарной маске (не по пустому фону между двумя разными
   полосами). Прошедшие обе проверки сшиваются кубической кривой Безье
   (гладкое продолжение касательных на концах).
9. **Фильтр по кривизне** (`filterByCurvature`) — линии со слишком большим
   средним углом поворота между соседними сегментами отбрасываются как
   вероятный шум/артефакт, а не настоящая гладкая полоса.

Метод даёт целочисленную (не суб-пиксельную) точность, зато полностью
глобален и не требует ни одной затравки — хорошо подходит как быстрый первый
проход по новому снимку.

## 4. Нумерация порядка полос и автозатравки

### 4.1 Автоматическая нумерация (`autoAssignFringeOrder`)

Файл: [`src/core/FringeOrdering.cpp`](../src/core/FringeOrdering.cpp).

Для трекеров на основе затравок (§3.1, §3.2) каждая линия независима —
трекер не знает про соседние линии и не присваивает номер сам. После
трассировки все полученные линии сортируются по СРЕДНЕМУ X всех своих точек и
нумеруются последовательно `0, 1, 2, ...` слева направо. Простая, но
достаточно надёжная эвристика для почти вертикальных полос без больших
взаимных перехлёстов по X.

`ScanlineExtremumTracker` (§3.3) — исключение: он уже вычисляет "настоящий",
топологически обоснованный номер через `FringeConstructor`, и этот номер
используется напрямую (`SetupStage.cpp:107-119`) вместо этой эвристики —
это физически точнее для изогнутых полос или полос, прерванных обструкцией
(там средний X может быть обманчив).

Пользователь может вручную переопределить номер любой линии
(`orderIsManual = true`, редактор в `ParametersDock`, "Fringe order
(double-click a line to edit)") — например, если автоматика ошиблась знаком
или сдвигом на константу (частая ситуация: абсолютный номер полосы всегда
известен только с точностью до общей аддитивной константы, если нет
дополнительной калибровки/реперной точки, см. S0b/S0c в §1 — пока не
реализованы).

### 4.2 Автоматическая расстановка затравок (`findRowSeeds`)

Файл: [`src/core/AutoSeedPlacement.cpp`](../src/core/AutoSeedPlacement.cpp).

Для трекеров §3.1/§3.2, которым нужна ровно одна затравка на полосу, есть
помощник — найти их автоматически по одной "хорошей" строке:

1. Находится строка с **максимальным числом видимых** (по маске апертуры)
   пикселей — не предполагается, что геометрический центр изображения вообще
   попадает в апертуру.
2. К этой строке применяется тот же алгоритм, что и в §3.3.1:
   `removeBackground` + `detectPeaks` — те же самые функции из
   `MiddleAlgorithm.cpp`, переиспользованные напрямую.
3. Каждый найденный пик становится затравкой `SeedPoint{x, bestY}`.

Т.е. это, по сути, "одна строка Scanline Extremum Method", использованная не
для полной трассировки, а только для генерации стартовых точек под другие
алгоритмы.

### 5.1 Horizontal Spline (построчный сплайн по трассированным линиям)

Файлы: [`PhaseReconstructor.{h,cpp}`](../src/core/pipeline/stages/phase_reconstruction/PhaseReconstructor.cpp),
обвязка в [`PhaseReconstructionStage.cpp`](../src/core/pipeline/stages/PhaseReconstructionStage.cpp),
подробная методичка — [`notes/phase-reconstruction.md`](phase-reconstruction.md).
Порт `WavefrontFromContoursSolver_HorizontalSpline` — метода, которым
оригинальный Digit реально формирует `.mtr` при экспорте (не путать с мёртвым
кодом решателя Лапласа в том же оригинале — см. ниже).

**Требует** предварительно трассированные и пронумерованные линии (§3–4).
Работает **независимо по каждой строке сетки** `y`:

1. **Пересечения** (`findFringeCrossings`) — для каждой пронумерованной линии
   ищутся точки пересечения с горизонталью `y = Y`: для наклонных сегментов —
   линейная интерполяция по Y с ПОЛУОТКРЫТЫМ правилом `[ymin, ymax)` (чтобы
   горизонталь, проходящая ровно через общую вершину двух соседних сегментов
   одной линии, не считалась дважды); для горизонтальных сегментов — просто
   середина сегмента. Каждое пересечение даёт пару `(x, order)`.
2. Пересечения сортируются по `x`.
3. Строится **натуральный кубический сплайн** через точки `(x, order)`
   (`NaturalCubicSpline`) — метод Томаса для трёхдиагональной системы
   уравнений на вторые производные, с натуральными граничными условиями
   (вторая производная на краях = 0). Меньше 2 пересечений в строке → вся
   строка остаётся `NaN` (сплайн через 1 точку не определён).
4. Сплайн вычисляется в каждом видимом пикселе строки, **включая
   экстраполяцию** за крайние пересечения — но экстраполяция **линейная**
   (касательная в конечной точке), не кубическая: кубический член натурального
   сплайна вне диапазона данных управляется кривизной СОСЕДНЕГО внутреннего
   узла, а не самими данными снаружи — из-за этого случайная разница в том,
   насколько далеко трассировка соседних строк дошла до края апертуры,
   раздувалась бы в заметный залом/загиб карты у самого края. Линейная
   экстраполяция ограничена по определению и держит край визуально прямым.

**Почему НЕ глобальное решение уравнения Лапласа `∇²z=0`** (историческая
развилка, подробно разобрана в `notes/phase-reconstruction.md`): раньше в
DigitQt стоял именно такой (математически "более элегантный") солвер —
линии как условия Дирихле, край апертуры как условие Неймана, решение методом
сопряжённых градиентов. Проблема — **гармоничность** (`∇²z=0`) физически
неверная гипотеза для реальных аберраций:

```
дефокус       z = ρ²        →  ∇²z = 4        (константа, не 0)
сферическая   z = ρ⁴        →  ∇²z = 16ρ²     (не 0)
```

Заставляя решатель заполнять промежутки между линиями ГАРМОНИЧЕСКОЙ
поверхностью, мы навязываем гипотезу нулевой кривизны везде, кроме самих
линий — а реальную кривизну девать некуда, и она "вытесняется" туда, где у
решателя ещё остаётся свобода: к краю апертуры и в узкие зоны вокруг линий.
Отсюда — характерные ложные загибы изолиний на концах линий и у края
апертуры, именно там, где у реальных аберраций (`~ρ²`, `~ρ⁴`) кривизна
МАКСИМАЛЬНА (значит, там же максимально и несовпадение с гармонической
гипотезой). Построчный сплайн этой проблемы не имеет: производная `dz/dx` в
каждой точке — это напрямую измеренное расстояние между полосами в данной
строке (метод "смотрит" именно в направлении поперёк полос, где фаза меняется
быстрее всего, и использует реальные данные как якорь и для значения, и для
наклона).

**Врождённый недостаток и его смягчение.** У полюса апертуры (где она узкая)
трассированные линии могут не пересекать горизонталь ≥ 2 раза — тогда ЦЕЛАЯ
строка остаётся `NaN`, даже если геометрически часть её пикселей видима
(**у оригинального Digit ровно то же ограничение** — это не потеря при
портировании). Второй проход в конце `reconstruct()` смягчает визуальный
артефакт (плоский горизонтальный "обрыв" вместо повторения формы апертуры):
для нерешённых видимых пикселей значение подтягивается **по вертикали** —
линейно между ближайшей решённой строкой сверху и снизу того же столбца
(или просто держится ближайшее значение, если решённые строки есть только с
одной стороны). Это не восстанавливает данные там, где трассировка реально не
дошла до края (для этого нужна лучшая трассировка на S1), но убирает сам
механизм, порождающий ложную горизонтальную линию.

**Ограничение метода в целом:** строки никак не связаны друг с другом (кроме
полюсной докомпенсации) — если полосы НЕ близки к вертикальным (почти
горизонтальные или сильно изогнутые полосы), метод менее надёжен: в строке
может оказаться мало пересечений, или они не будут монотонны по X в
физическом смысле. Оригинал имеет то же ограничение.

### 5.2 Fourier Transform Method (Такеда, 1982)

Файлы: [`FourierPhaseExtractor.{h,cpp}`](../src/core/pipeline/stages/phase_reconstruction/FourierPhaseExtractor.cpp).

Классический метод пространственно-несущего анализа полос (spatial-carrier
fringe pattern analysis), не требующий трассировки линий вообще — фаза
извлекается сразу во всей апертуре одним 2D БПФ.

**Физическая идея.** Интерферограмма с наклонной несущей (§0.3) —
периодический (по несущей частоте) сигнал, промодулированный медленно
меняющейся фазой аберрации:

```
I(x,y) = a(x,y) + b(x,y)·cos(2π·f0·x + φ_aberr(x,y))
       = a(x,y) + (b/2)·exp(i(2π·f0·x + φ)) + (b/2)·exp(-i(...))
```

В 2D-спектре Фурье такого сигнала — три пика: центральный (постоянная
составляющая + медленные вариации `a(x,y)`, вокруг нулевой частоты) и два
симметричных БОКОВЫХ пика на частоте несущей `±f0`, каждый из которых несёт
ПОЛНУЮ информацию об искомой фазе `φ(x,y)` (один — как `φ`, другой как `-φ`,
комплексно сопряжённые).

**Алгоритм (`extract`):**

1. **Аподизация края апертуры** — приподнятый косинус (raised-cosine window)
   от края апертуры вглубь на `kTaperWidth = 40` px (через `distanceTransform`
   до внешней границы маски). Резкий обрыв яркости на краю апертуры даёт
   мощный "крест" паразитных частот в спектре, который иначе полностью
   забивает настоящий боковой пик несущей — проверено экспериментально, без
   этого шага метод не работает вообще.
2. **2D БПФ** (`cv::dft`) + `fftShift` (перенос нулевой частоты в центр
   спектра для удобства визуального/алгоритмического поиска).
3. **Поиск бокового пика** — максимум модуля спектра `|F|` вне окрестности DC
   (радиус `kDcRadius = 8` px вокруг центра исключается). Если пик слишком
   близко к центру (не отделяется от DC) — ошибка: несущая слишком слабая
   или полосы отсутствуют.
4. **Гауссов полосовой фильтр** вокруг найденного пика, радиус `0.6 ×
   расстояние_до_DC` — вырезает именно нужный боковой лепесток, отбрасывая
   всё остальное (второй боковой пик, DC, шум).
5. **Демодуляция** — отфильтрованный спектр циклически сдвигается так, чтобы
   найденный пик оказался в центре (это и есть перенос несущей частоты в
   ноль — операция, эквивалентная умножению исходного сигнала на
   `exp(-i·2π·f0·x)` в пространственной области), затем обратное БПФ
   (`cv::idft`).
6. **Свёрнутая фаза** — результат обратного БПФ комплексный;
   `φ_wrapped(x,y) = atan2(Im, Re)` — это фаза, "свёрнутая" в диапазон
   `(-π, π]` (стандартная неоднозначность `arctan`, физически — реальная фаза
   известна только `mod 2π`).
7. **Разворачивание фазы (unwrap)** — заливка (BFS) от одной точки (центра
   масс апертуры или первой видимой точки): для каждого нового пикселя
   сравнивается его свёрнутое значение с уже развёрнутым значением соседа,
   и вычитается ближайшее кратное `2π`, приводящее два значения в согласие
   (`k = round((wv - base)/2π)`). Результат — гладкая (без скачков на `2π`)
   карта фазы по всей связной апертуре.
8. **Восстановление наклона.** Демодуляция на шаге 5 буквально ВЫЧИТАЕТ
   несущую частоту как часть переноса спектра — значит, после разворачивания
   общий наклон (тот самый преднамеренный carrier tilt из §0.3) почти
   полностью пропадает из результата. Он восстанавливается явно из самого
   положения найденного пика в спектре: пик на `(peakX, peakY)` соответствует
   пространственной частоте `carrierFreqX = (peakX-cx0)/W` циклов/пиксель по
   x (аналогично по y), что переводится обратно в фазовую плоскость
   `carrierPhase = 2π·(fx·(x-cx_ap) + fy·(y-cy_ap))` и складывается с
   развёрнутым остатком. Без этого шага наклон был бы систематически занижен
   в десятки раз (проверено экспериментально).

Итог делится на `2π`, давая ту же единицу измерения (порядок полосы `N`), что
и у построчного метода (§5.1) — так `WavefrontReconstructionStage` (§6)
работает одинаково независимо от того, какой алгоритм S2 использовался.

Метод валидирован на синтетических данных с заранее известными
коэффициентами аберраций — дефокус/астигматизм/кома/трефойл/сферическая
восстанавливаются точно.

### 5.3 Wavelet Transform Method (Zhong & Weng, 2004)

Файлы: [`WaveletPhaseExtractor.{h,cpp}`](../src/core/pipeline/stages/phase_reconstruction/WaveletPhaseExtractor.cpp).

Локально-адаптивная альтернатива методу Фурье (§5.2): вместо ОДНОЙ несущей
частоты на всё изображение (глобальный пик БПФ), частота ищется **отдельно в
каждой точке** через непрерывное вейвлет-преобразование (Continuous Wavelet
Transform, CWT) вдоль строки.

**Комплексный вейвлет Морле:**

```
ψ(t) = exp(i·ω0·t) · exp(-t²/2),   ω0 = 5.5
```

(`ω0 = 5.5` — стандартный в литературе по WTP компромисс между разрешением
по частоте и по пространству: больше `ω0` — точнее частота, но хуже
локализация во времени/пространстве, и наоборот). CWT сигнала `s(x)` на
масштабе `a` в точке `x`:

```
W(a,x) = (1/√a) · Σ_τ s(τ) · ψ*((τ-x)/a)
```

где `ψ*` — комплексно сопряжённый вейвлет. Это, по сути, локальная свёртка
сигнала с "окном", которое одновременно и осциллирует с частотой `~ω0/a`, и
затухает по Гауссу с шириной `~a` — т.е. одновременно даёт информацию и о
частоте, и о положении (в отличие от глобального БПФ, дающего частоту, но
теряющего локализацию).

**Алгоритм (`extract`):**

1. **Грубая оценка периода несущей** (`estimateCarrierPeriod`) — ОДНО
   глобальное 2D БПФ (как в §5.2, шаг 2-3), но используется только чтобы
   задать РАЗУМНЫЙ диапазон масштабов для следующего шага — точность этой
   оценки не критична, реальную (локальную) частоту ищет уже сам гребень CWT.
2. **Набор масштабов** — 16 масштабов `scales[i]`, логарифмически (на октаву в
   каждую сторону) вокруг грубой оценки периода `period0`, от `0.5·period0`
   до `2·period0`. Для каждого масштаба заранее считается ядро свёртки
   (`re[]`/`im[]` — вещественная и мнимая части комплексно-сопряжённого
   вейвлета), с носителем (`support`) до `3σ` (`kSupportSigmas`), не длиннее
   `kMaxSupport = 120` px.
3. **Гребень CWT (ridge)** — для каждой видимой точки `(x,y)` вдоль строки
   вычисляется свёртка с КАЖДЫМ из 16 ядер, берётся масштаб `a*` с
   МАКСИМАЛЬНЫМ модулем `|W(a,x)|` — это и есть локальная оценка частоты в
   данной точке (гребень CWT в плоскости "масштаб-положение"); свёрнутая фаза
   в этой точке — `arg(W(a*,x))`. Одномерный (только вдоль x, построчно) —
   вейвлет Морле здесь одномерный.
4. **Разворачивание (unwrap)** — та же 2D BFS-заливка от одной точки, что и в
   §5.2 (переиспользован тот же приём).
   
   > Историческая деталь реализации: раньше строки разворачивались НЕЗАВИСИМО
   > (только по соседям вдоль x), а согласование между соседними строками
   > делалось отдельным проходом по столбцам, сравнивающим с ОДНИМ пикселем
   > сверху. На практике ненадёжно: соседние строки могли независимо
   > "соскочить" на целое число периодов из-за шума, а подгонка по одному
   > соседу не всегда это выправляла — на чистом наклоне без единой
   > аберрации это давало ложные "астигматизм"/"дефокус" в разы больше нуля.
   > 2D-заливка от единого центра, сравнивающая каждый новый пиксель сразу со
   > ВСЕМИ 4 уже развёрнутыми соседями, структурно устраняет саму возможность
   > такой рассинхронизации между строками.

Результат, как и в §5.1–5.2, делится на `2π` и хранится в единицах порядка
полосы. Трассировка (S1) для этого метода не запускается (`SetupStage.cpp:21-29`
явно очищает список линий, если выбран Фурье- или вейвлет-метод).

### 5.4 Когда какой метод выбирать

| Метод | Плюсы | Минусы / когда не подходит |
|---|---|---|
| Horizontal Spline | Тот же алгоритм, что даёт оригинальный Digit при экспорте `.mtr` — совместимость по числам. Полный контроль пользователя над трассировкой (можно вручную поправить ошибочные линии/номера). | Требует качественной трассировки S1 (шум в линиях = шум в фазе). Плохо работает при почти горизонтальных/сильно изогнутых полосах. Врождённая проблема на полюсе апертуры (§5.1). |
| Fourier Transform | Не требует трассировки вообще — быстрый результат по всей апертуре сразу. Точен при чистой однородной несущей. | Нужна ОДНА хорошо выраженная несущая частота на весь снимок; плохо работает при сильно переменном локальном периоде полос или без несущей вовсе (замкнутые кольца). Чувствителен к резкому краю апертуры (см. аподизацию). |
| Wavelet Transform | Локально-адаптивная частота — устойчивее Фурье там, где период полос заметно меняется по полю из-за сильных аберраций. | Дороже по вычислениям (свёртка с 16 ядрами в каждой точке). Всё ещё нужна распознаваемая несущая (грубая оценка периода на шаге 1). |

## 6. Реконструкция волнового фронта (S4)

Файл: [`WavefrontReconstructionStage.cpp`](../src/core/pipeline/stages/WavefrontReconstructionStage.cpp).

порядка полосы" (числа) в физические единицы длины (нанометры):

```cpp
heightPerOrder = measurement.isDoublePass() ? wavelengthNm / 2 : wavelengthNm;
wavefront(x,y) = phase(x,y) * heightPerOrder;
```

Смысл коэффициента `λ/2` разобран в §0.2 (отражательная, double-pass схема —

интерферометрии источника). Переключатель `isDoublePass()` — на странице S4
в `ParametersDock`.

## 7. Модальный анализ / разложение по Цернике (S5)

Файлы: [`ModalAnalysisStage.cpp`](../src/core/pipeline/stages/ModalAnalysisStage.cpp),

[`ModalFitMethod.h`](../src/core/ModalFitMethod.h).

### 7.1 Зачем раскладывать волновой фронт на полиномы

Карта высот `wavefront(x,y)` (S4) — это уже "настоящая" форма поверхности
относительно идеально плоской/сферической, НО она всё ещё смешивает две вещи:

1. **Погрешности самой ГЕОМЕТРИИ измерения** — наклон и юстировка образца в
   держателе (`tiltX`, `tiltY`), расфокусировка интерферометра (`defocus`).
   Это не свойство поверхности, а артефакт того, КАК образец был установлен
   при съёмке — их нужно вычесть, чтобы увидеть реальное качество.
2. **Реальные особенности формы поверхности** — то, что действительно
   интересует метролога/оптика: астигматизм, кома, сферическая аберрация,
   трефойл и — самое главное — **остаток** (residual) после вычитания всех
   этих низкочастотных членов, который показывает мелкую, "нерегулярную"
   структуру поверхности (например локальные дефекты полировки).

Модальный анализ — это **аппроксимация методом наименьших квадратов (МНК)**:
подобрать коэффициенты полиномов, наилучшим образом приближающих карту
высот, затем изучать отдельно (а) коэффициенты (величина каждой аберрации) и
(б) остаток (карта минус подгонка).

### 7.2 Базис термов: не "учебниковые" полиномы Цернике, а Seregin/DAPPSIM

Важная деталь реализации: базисные функции — это **прямая транскрипция**
полиномов из референсного инструмента DAPPSIM (метод Серёгина), а НЕ
стандартные ортонормированные полиномы Цернике из оптических учебников. Это
осознанный выбор совместимости — коэффициенты на выходе получаются в тех же
единицах и с тем же знаком, что и у референсного инструмента, с которым
сверяются результаты.

Нормализованные зрачковые координаты `(x, y) ∈ [-1, 1]` (край апертуры ровно
на радиусе 1, стандартное соглашение в оптике). Важная деталь знака: DAPPSIM
использует оптическое соглашение "Y растёт вверх"
(`Y_optical = -(y_sample - y0)/r0`), тогда как нормализованная координата
сэмпла `y` в этом коде растёт вниз по строкам изображения (обычное соглашение
для растровых изображений) — переворот сделан прямо в формулах ниже, там, где
`Y` входит в нечётной степени:

```
piston      1
tiltX       x                        tiltY      -y
defocus     x²+y²
astigX      1.5(x²-y²)               astigY     -xy
comaX       x³+xy²-(2/3)x            comaY      (2/3)y - y³ - x²y
trefoilX    3xy²-x³                  trefoilY   3x²y-y³
spherical   (x²+y²)²
```

**Про астигматизм — историческая деталь.** У Серёгина астигматизм на самом
деле подгоняется ТРЕМЯ коэффициентами: `(3x²-1)/2`, `xy`, `(3y²-1)/2` — но
первый и третий термы НЕ ортогональны дефокусу (в сумме дают ещё один
дефокус-подобный член) — исторический артефакт последовательной (не
Грам-Шмидт) схемы подгонки DAPPSIM, где термы подгоняются по одному, а не все
сразу. `astigX` здесь — эквивалент их РАЗНОСТИ
(`1.5(x²-y²) = ((3x²-1)/2 - (3y²-1)/2)`), т.е. "чистый" астигматизм без
дефокусной примеси; `astigY` — их крест-терм (`xy`) как есть.

### 7.3 Два способа решения МНК

`Measurement::modalFitMethod()` — выбор из двух:

**`JointLeastSquares`** — обычный совместный МНК по фиксированному базису
`buildTermHierarchy()` для ВСЕХ выбранных пользователем термов сразу (не по
стадиям, как исторический Серёгин). Матрица `A` (строка — точка сетки,
столбец — терм), решение через `QR`-разложение с выбором ведущего столбца
(`colPivHouseholderQr`, устойчивый метод решения переопределённой системы).
Термы не ортогонализуются — это значит, что физически коррелирующие члены
одной "радиальной семьи" (пистон/дефокус/сферическая — все зависят только от
`ρ² = x²+y²`; наклон/кома — оба линейны по своей оси) могут "делить" вклад
между собой в зависимости от того, какое ИМЕННО подмножество термов выбрано
галочками в UI. Даёт коэффициенты в тех же единицах, что и DAPPSIM/WinFringe.

**`GramSchmidtOnAperture`** — дополнительная численная ортогонализация того
же базиса (процесс Грама-Шмидта) **прямо по фактическим точкам данной
апертуры** (не по формуле для идеального круга — работает для апертуры любой
формы, в том числе с вырезами/обструкциями): термы обрабатываются в
фиксированном порядке (пистон → наклон → ... → сферическая), каждый следующий
явно избавляется от проекции на все предыдущие (`col -= (col·prev/‖prev‖²)·prev`).
После этого включение/выключение одного чекбокса ГАРАНТИРОВАННО не меняет
коэффициент остальных выбранных термов — ценой того, что коэффициенты уже не
совпадают напрямую с другим ПО (только суммарная невязка RMS/PV совпадает с
`JointLeastSquares`, если подгонять всё сразу).

### 7.3.1 Базис термов: Seregin или классический Цернике (`PolynomialBasis`)

Отдельный от `ModalFitMethod` переключатель — `Measurement::polynomialBasis()`
(`PolynomialBasis::Seregin` по умолчанию, или `Zernike`), UI — комбобокс
"Polynomial basis" на странице S5 в `ParametersDock`. Ортогонален выбору
"как решать МНК" из §7.3: любая из двух комбинаций способа × базиса
работает.

`PolynomialBasis::Zernike` (`buildZernikeHierarchy()` в
`ModalAnalysisStage.cpp`) — классические (учебниковые, неортонормированные)
полиномы Цернике в тех же зрачковых координатах `x,y ∈ [-1,1]`:

```
piston      1
tiltX       x                        tiltY      y
defocus     2(x²+y²)-1
astigX      x²-y²                    astigY     2xy
comaX       (3(x²+y²)-2)x            comaY      (3(x²+y²)-2)y
trefoilX    x³-3xy²                  trefoilY   3x²y-y³
spherical   6(x²+y²)²-6(x²+y²)+1
```

Важное отличие от Seregin: здесь `y` — **сырая** координата сэмпла (растёт
вниз по строкам изображения), БЕЗ оптического переворота Seregin (§7.2).
Значит, для одного и того же физического волнового фронта `tiltY`/`astigY`/
`comaY`/`trefoilY` в базисе Zernike получаются с **противоположным знаком**
относительно Seregin — это не баг, а разница конвенции "куда считать
положительным Y", и она заложена намеренно: эта опция существует именно
для сравнения с внешними инструментами/генераторами интерферограмм,
которые почти всегда используют "сырой" Y (растровый, вниз), а не
оптическую конвенцию DAPPSIM.

**Формула перевода** (выведена почленным сравнением многочленов по каждой
степени `x,y` отдельно, проверена на реальных данных — импорт одного и
того же `.mtr` в оба базиса даёт совпадение до 4-5 значащих цифр, см.
историю обсуждения; ниже `_ser` = коэффициент в базисе Seregin, `_zern` —
в базисе Zernike, для одной и той же физической поверхности):

```
tiltX_ser     = tiltX_zern
tiltY_ser     = −tiltY_zern
defocus_ser   = 2·defocus_zern − 6·spherical_zern
astigX_ser    = (2/3)·astigX_zern
astigY_ser    = −2·astigY_zern
comaX_ser     = 3·comaX_zern
comaY_ser     = −3·comaY_zern
trefoilX_ser  = −trefoilX_zern
trefoilY_ser  = trefoilY_zern
spherical_ser = 6·spherical_zern
```

Наклон переводится ЧИСТО (без кросс-члена с комой) — это не случайность:
у обеих формул комы (Zernike `(3ρ³-2ρ)cosθ` и Seregin `x³+xy²-(2/3)x`) есть
собственный "довесок" линейной по x/y степени (`-2ρ·cosθ` и `-(2/3)x`
соответственно), специально подобранный, чтобы кома была ортогональна
наклону. При аккуратном сравнении по степеням эти два "довеска" (со своими
масштабными множителями `comaX_ser=3·comaX_zern`) взаимно уничтожаются,
оставляя чистое `tiltX_ser = tiltX_zern`.

> **Историческая деталь.** Раньше здесь стояла неверная версия с кросс-членом
> (`tiltX_ser = tiltX_zern − 2·comaX_zern`) — при выводе была пропущена
> собственная линейная составляющая Seregin-формы комы (`-(2/3)x`), не
> только у Zernike-формы. Поймано при импорте одного `.mtr` в оба базиса:
> реальный наклон совпадал с формулой без кросс-члена и расходился с
> формулой, где он был.

Дефокус/сферическая "смешиваются" между собой при переводе — это отражает
реальную математику: полином Цернике `6ρ⁴-6ρ²+1` **сам по себе** уже
содержит более низкую степень `ρ`, тогда как "голые" мономы Seregin
разносят каждую степень по отдельному члену. У комы/трефойла такого
смешения между СОБОЙ нет (только внутренний, самокомпенсирующийся довесок
у комы, разобранный выше) — поэтому в переводе трефойла кросс-члена с
комой тоже нет.

Трефойл переводится ЧИСТО 1:1 (со знаком), без дополнительного множителя —
это специально проверено алгебраически (раскрытием `x³-3xy²`/`3x²y-y³`
почленно против Seregin-формы `3xy²-x³`/`3x²y-y³`), поэтому здесь НЕ
заложена никакая эмпирическая поправка вида "×2" — если сторонний
инструмент показывает трефойл вдвое больше учебникового, это особенность
ЕГО собственной конвенции отображения, а не то, что нужно компенсировать
здесь.

Проверено юнит-тестом `ModalAnalysisStageTest::exactRecoveryMatchesZernikeBasis`
(точное восстановление, как и для Seregin в §7.3, на синтетической
поверхности, построенной по этим же формулам).

### 7.4 Область подгонки: зрачковые координаты и эрозия края

Центр и радиус апертуры для нормализации берутся из **фактического
bounding-box** непустых пикселей КАРТЫ (не из `Measurement::boundaries()` —
те заданы в координатах полного изображения, а карта может храниться на
уменьшенной сетке решения, см. `kMaxGridDimension` в §5.1). Раньше нормировка
шла по размеру ИЗОБРАЖЕНИЯ целиком; если апертура не занимает весь кадр
(обычно так и есть), это давало ложную крутизну термов высокой степени
(кома/трефойл/сферическая) ближе к настоящему краю апертуры — полиномы
высокой степени особенно чувствительны к ошибке масштаба у края.

**Эрозия края** (`edgeErosionPixels`, по умолчанию 2 px) — перед подгонкой
из выборки исключаются пиксели, у которых хоть один сосед в этом радиусе не
имеет данных (гарантированно граничные, даже если формально сами входят в
апертуру). Мотивация: самый крайний ободок карты фазы — систематически
наименее надёжные данные (вертикальная докомпенсация полюса из §5.1,
экстраполяция построчного сплайна и т.п. концентрируются именно там); одна
такая аномальная точка на глобальном МНК не "усредняется", а даёт локальный
выброс ровно в этой точке — на 3D-графике остатка это выглядит как отдельные
"иглы" у края.

### 7.5 Результат

`ModalAnalysisResult` хранит: подогнанные коэффициенты (`ModalCoefficients`,
в тех же единицах, что и `wavefrontMap` — нанометры), какие термы реально
участвовали (`selection`), карту остатка (`residual = карта - подгонка`,
`NaN` вне выборки) и `rmsBefore`/`rmsAfter` (среднеквадратичное отклонение
карты от нуля до и после вычитания подогнанных термов — насколько "чище"
стал остаток).

## 8. Экспорт в WinFringe: .mtr и .frn

Оба формата — не собственный формат DigitQt, а совместимость со сторонней
программой WinFringe (для дальнейшего анализа/сравнения результатов).

### 8.1 `.mtr` — карта волнового фронта

Файл: [`src/io/MtrExporter.cpp`](../src/io/MtrExporter.cpp).

Текстовый формат: квадратная матрица значений `Z` на регулярной сетке,
нормализованной в квадрат `[-1,1]×[-1,1]`, с указанием пар `(Z, X_norm)` по
строкам с `Y_norm` в начале строки.

Ключевые шаги:
1. **Минимальная охватывающая окружность** данных (`minEnclosingCircle`,
   классический **алгоритм Уэлзла** — рандомизированный, ожидаемая линейная
   сложность `O(n)`: рекурсивно строит минимальный круг через первые `n`
   точек, "поддерживая" на границе не более 3 опорных точек; если очередная
   точка не попадает в уже построенный круг для первых `n-1` точек — круг
   обязан пройти через эту точку, и она добавляется в опорные) — строится по
   крайним левому/правому видимым столбцам КАЖДОЙ строки (не по всем
   пикселям маски — так же, как в оригинальном `computeMaskBoundingCircle`).
2. Размер матрицы — диаметр этой окружности, округлённый до нечётного числа
   (`sizeMatrix |= 1`, для симметрии сетки вокруг центра).
3. **Инверсия Y**: карта хранится в экранной системе координат (Y растёт
   вниз), а `.mtr`/WinFringe ожидает математическую (Y растёт вверх) — как и
   оригинальный Digit, явно конвертирующий `SCREEN → MATH` перед экспортом.
   Без этого шага `TiltY` попадает в файл с обратным знаком.
4. Значения `X_norm, Y_norm` вне диапазона `[-1,1]` отбрасываются (портят
   расчёты WinFringe при загрузке).

### 8.2 `.frn` — апертура и линии полос

Файл: [`src/io/FrnExporter.cpp`](../src/io/FrnExporter.cpp).

Реализован только "WinFringe-вариант" формата (Y перевёрнут + нормализация) —
альтернативный "родной" вариант Digit (сырые пиксельные координаты) не
портирован, т.к. не был нужен.

Содержит секции:
- `[GENERAL]` — метаданные (дата, масштаб).
- `[ELLIPSES]` / `[RECTANGLES]` / `[POLYGONS]` — фигуры апертуры EXTERNAL и
  INTERNAL (WinFringe поддерживает только 2 типа обскурации: `0=internal,
  1=external` — противоположно внутреннему `aperture::TypeLimits`, где
  `EXTERNAL=0`; при экспорте это явно инвертируется). Тип DigitQt `APERTURE`
  ("локальное окно", §0.4) аналога в этом формате не имеет — такие фигуры
  при экспорте пропускаются. Все фигуры перед записью переворачиваются по Y
  и нормализуются в единицы, где охватывающая окружность апертуры (см. ниже)
  имеет радиус 1.
- `[BOUNDS]` — по одной строке на НЕповёрнутый эллипс/прямоугольник (без
  нормализации); повёрнутые и внутренние (INTERNAL) прямоугольники WinFringe
  здесь не поддерживает.
- `[FRINGES]` — по блоку `NFringe=<order>` на каждую пронумерованную
  трассированную линию, со всеми её точками (Y тоже перевёрнут).
- `[IMAGE_FILE]` — размер и имя исходного файла изображения.

Охватывающая окружность здесь — не `minEnclosingCircle` по данным карты, а
`computeWinFringeBoundCircle` (порт оригинального `CalcWinFringeBoundCircle`):
берутся точки контура ВСЕХ НЕповёрнутых EXTERNAL-эллипсов/прямоугольников
(полигоны не участвуют — так и в оригинале), отфильтрованные по фактической
видимости через `VisibilityChecker` (так пересечение нескольких EXTERNAL-фигур
и INTERNAL-обструкции учитываются автоматически), и через них строится тот же
алгоритм Уэлзла.

### 9.2 Термины (RU ⇄ EN)

| Термин | Пояснение |
|---|---|
| Разность хода, OPD | Optical Path Difference — на сколько один луч длиннее другого |
| Порядок полосы, fringe order `N` | Число длин волн разности хода в данной точке |
| Несущая, carrier (frequency/tilt) | Намеренный наклон опорного пучка, создающий регулярную решётку полос-носителей |
| Развёртывание фазы, phase unwrapping | Восстановление непрерывной (не `mod 2π`) фазы из свёрнутой |
| Апертура, aperture | Рабочая область измерения (зрачок) |
| Обструкция, obstruction (INTERNAL) | Область внутри апертуры, лишённая данных |
| Гребень (полосы), ridge | Линия локального экстремума яркости — центр полосы |
| Скелетизация, skeletonization | Утончение бинарного изображения до линий толщиной 1 пиксель |
| Структурный тензор, structure tensor | Матрица моментов градиента, даёт локальное направление текстуры |
| Zernike / Seregin полиномы | Базисные функции для разложения формы волнового фронта по низкочастотным аберрациям |
| PV, Peak-to-Valley | Размах карты (максимум минус минимум) |
| RMS | Среднеквадратичное отклонение карты от нуля |
